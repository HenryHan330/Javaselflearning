## 4. 知识点（待补充）
### 4.1 JVM 是什么 / 运行流程

Java 代码的运行分两步：**编译期**先把源码编译成字节码，**运行期**再由 JVM 把字节码变成机器码。

```text
编译期：Java 源码(.java) --javac 编译--> 字节码(.class)
运行期：字节码 --JVM--> [ 解释执行 | JIT 即时编译 ] --> 机器码
```

- **字节码**：与平台无关的中间表示，由 JVM 负责翻译成当前平台的机器码。
- **解释执行**：直接逐条解释字节码并运行，不用等编译。
- **JIT（即时编译）**：运行时把**热点代码**编译优化成机器码并缓存，避免反复解释，从而提升性能。

两种执行方式：

- **解释执行**：直接逐条运行字节码——启动快，但同一段代码反复执行时开销大。
- **JIT 编译**：运行时把热点代码编译优化成机器码——编译本身有开销，但热点代码执行快。

一句话：**JVM 用「解释执行 + JIT 编译」混合的方式跑字节码——冷代码靠解释，热代码靠编译。**

### 4.2 类文件结构（了解即可）

编译产物就是 `.class` 文件（字节码）。里面无非是：**魔数、版本号、常量池、字段表、方法表**。日常不用背格式，知道有这些东西就行。

想亲手看看这些内容，用 JDK 自带的**反编译命令 `javap`**——不会用就先敲 `javap -help` 看基本用法。

工作中真正会碰到它的 4 个地方：

1. **`UnsupportedClassVersionError`** —— 报错里会带 `class file version 61.0` 这类数字，就是类文件里的**版本号**。常见原因：用高版本 JDK 编译、低版本 JDK 运行。看懂它能快速定位环境问题。
2. **`javap -v` 看字节码** —— 想确认「这段代码被编译成了啥」时用（字符串拼接、`switch`、自动装箱的真实行为）。
3. **字节码增强** —— Lombok、AOP（CGLIB / ASM / ByteBuddy）、热部署、监控探针，都是在运行时修改字节码。
4. **反编译** —— 想看第三方库或老代码的内部实现时，反编译出来的就是类文件内容。

#### 字节码指令（了解即可）

按功能分九类：

1. **加载和存储**：在**局部变量表**和**操作数栈**之间搬数据。常见有 `iload` / `istore` / `aload`、`ldc`、`iconst_1`。
2. **运算**：在操作数栈上做加减乘除、位运算。如 `iadd`、`isub`、`imul`、`idiv`、`iand`。
3. **类型转换**：一种类型转成另一种。如 `i2l`、`i2f`、`l2i`、`f2d`、`i2b`。
4. **对象创建与访问**：`new` 对象、读写字段、取数组长度。如 `new`、`newarray`、`getfield`、`putfield`、`getstatic`、`putstatic`、`arraylength`。
5. **操作数栈管理**：摆弄操作数栈本身（弹掉、复制、交换）。如 `pop`、`dup`、`swap`。
6. **控制转移**：`if` / 循环 / `switch` 的跳转。如 `ifeq`、`if_icmpgt`、`goto`、`tableswitch`、`lookupswitch`。
7. **方法调用和返回**：调方法、把结果还给调用者。如 `invokevirtual`、`invokespecial`、`invokestatic`、`invokeinterface`、`invokedynamic`、`ireturn`。
8. **异常处理**：抛异常。如 `athrow`。
9. **同步**：`synchronized` 的加锁 / 解锁。如 `monitorenter`、`monitorexit`。

**重点看第 1 类「加载和存储」**——它是使用最频繁的指令，负责在**局部变量表**和**操作数栈**之间来回搬数据。

指令名开头的字母表示类型：`i`=int、`l`=long、`f`=float、`d`=double、`a`=引用。

**① 加载 load：局部变量表 → 操作数栈**

- `iload_1`：把局部变量表中下标为 1 的 int 变量压入操作数栈
- `aload_2`：把下标为 2 的引用类型变量（此时为 String）压入操作数栈
- `lload_3`：把下标为 3 的 long 型变量压入操作数栈

**② 把常量压入操作数栈**（不经过局部变量表，按数值范围细分）

- `iconst` 系列：范围 `[-1, 5]`。
- `bipush`：范围 `[-128, 127]`（一个字节）。
- `sipush`：范围 `[-32768, 32767]`（两个字节）。
- `ldc`：其他 int（如 `32768`），以及字符串、类引用等。

**③ 存储 store：操作数栈 → 局部变量表**

主要用于**给局部变量赋值**，以 `store` 形式存在，例如 `istore_1`（把操作数栈顶的 int 存进局部变量表下标 1）。

**④ 运算（算术）指令**

- 加法：`iadd`、`ladd`、`fadd`、`dadd`
- 减法：`isub`、`lsub`、`fsub`、`dsub`
- 乘法：`imul`、`lmul`、`fmul`、`dmul`
- 除法：`idiv`、`ldiv`、`fdiv`、`ddiv`
- 求余：`irem`（另有 `lrem` / `frem` / `drem`）
- 自增自减：`iinc`（`i++` 就是 `+1`，`i--` 就是 `-1`）

**⑤ 类型转换指令**

- **宽化（widening）**：小类型 → 大类型，如 `int → long → float → double`。指令如 `i2l`、`i2f`、`i2d`、`l2f`、`l2d`、`f2d`。
- **窄化（narrowing）**：大类型 → 小类型，如 `long` / `int` → `byte` / `short` / `char`，需要强制转换、可能丢精度。指令如 `l2i`、`f2i`、`d2i`、`i2b`、`i2c`、`i2s`。

**⑥ 方法调用指令（5 个）**

- `invokevirtual`：调用对象的成员方法，按对象的**实际类型**分派，支持多态。
- `invokeinterface`：调用接口方法，运行时搜索由特定对象实现的接口方法。
- `invokespecial`：调用需要特殊处理的方法：**构造方法、私有方法、父类方法**。
- `invokestatic`：调用静态方法。
- `invokedynamic`：运行时动态解析出调用点所引用的方法再执行（Lambda 用得多）。

**⑦ 操作数栈管理指令**

- **弹出并废弃**：`pop`（一个槽）、`pop2`（两个槽）
- **复制栈顶并重新压入**：`dup`、`dup2`、`dup_x1`、`dup2_x1`、`dup_x2`、`dup2_x2`
- **交换栈顶两个槽**：`swap`

### 4.3 运行时数据区

承接上文：字节码数据和运行时产生的中间数据，都需要一块地方存下来，这就是**运行时数据区**。

它一共分成五块，按「归谁所有」可以分成两类：**程序计数器、虚拟机栈、本地方法栈是线程私有的**，跟着线程生、跟着线程死；**堆和方法区是线程共享的**，所有线程一起用，也是垃圾回收的主战场。下面挨个过。

**程序计数器**是五块里最小的一块，每个线程都有自己独立的一个。它存的东西很简单，就是**当前线程下一条要执行的字节码指令的地址**，你可以把它理解成看书时夹的那根书签，记录「读到哪了」。之所以必须线程私有，是因为在多核环境下 CPU 的时间片是轮流分给各个线程的，线程被切走再切回来，得靠它找回原来的执行位置；分支、循环、跳转、异常处理，本质上也都依赖它。还有一点值得留意：如果当前线程执行的恰好是一个 `native` 方法（C/C++ 实现的），程序计数器的值会是 `undefined`，因为 native 方法不是字节码，没有「行号」可记。最后，它是运行时数据区里**唯一一个不会抛 OOM 的区域**——它只存一个行号，占多大是固定的，不会涨。

**虚拟机栈**描述的是 Java 方法执行的内存模型。每调用一个方法，JVM 就为它压入一个**栈帧**，方法执行完栈帧随之弹出，所以栈的生命周期和线程完全一致。栈帧里装着四样东西：局部变量表（放方法参数和局部变量，包括 `this`）、操作数栈（计算时的临时工作区）、动态链接（指向运行时常量池中本方法所属类的引用）、返回地址（方法执行完该回到哪一行）。它出问题有两种典型形态：一是**栈太深**，比如递归层数过多、调用链太长，超过了 `-Xss` 设定的单线程栈容量，于是抛 `StackOverflowError`；二是**线程太多**，每个栈虽然不大，但架不住线程数量爆炸，本地内存不够创建新线程，于是抛 `OutOfMemoryError: unable to create native thread`。后一种特别容易被误解成堆的问题，其实跟堆一点关系都没有，堆调大反而更糟。

**本地方法栈**和虚拟机栈几乎是一对孪生兄弟，只不过它是为 `native` 方法服务的，结构和异常表现都一样。在实际用的 HotSpot 虚拟机里，它和虚拟机栈**已经合并成一块**了，所以这块平时不用分开记，面试时提一句「HotSpot 里二者合并」就够了。

**堆**是运行时数据区里最大的一块，也是唯一存放对象实例和数组的地方（准确说是「几乎所有对象」）。它被所有线程共享，是**垃圾回收的主战场**，因此被拆成了分代结构：新生代约占三分之一，里面又分出一个 Eden 和两个 Survivor（默认比例 8:1:1）；老年代约占三分之二。对象正常情况下先在 Eden 里分配，一次 Minor GC 后还活着的挪进 Survivor，在两个 Survivor 之间来回倒腾，熬过默认 15 次 GC 还活着的、或者一开始就特别大的对象，直接晋升到老年代，老年代满了就触发 Full GC。日常调堆用 `-Xms`（初始大小）和 `-Xmx`（最大大小），线上一般把这两个值设成一样，免得堆反复扩容收缩带来性能抖动。堆里还有两个值得知道的概念：一个是 **TLAB**，Eden 里预先给每个线程划的一小块私有缓冲区，分配对象时就不用抢锁了，默认开启；另一个是**逃逸分析**，如果 JIT 发现某个对象不会「逃出」当前方法，就可能把它拆成标量直接放到栈上（标量替换），所以「对象一定分配在堆上」这句话严格来说并不成立。

**方法区**存的是**类的元信息**——类名、父类、接口、字段、方法、修饰符、方法字节码等等，也就是一个类被加载进来之后那些不常变的结构信息，另外还包含运行时常量池、静态变量和 JIT 编译后的代码缓存。这里有个常见的望文生义：它**不是「存方法的地方」**，而是「存这个类的结构信息的地方」。方法区的实现经历过一次大变：JDK 7 及以前它叫**永久代（PermGen）**，属于堆的一部分，用 `-XX:PermSize / -XX:MaxPermSize` 控制，典型故障是 `OutOfMemoryError: PermGen space`；JDK 8 起永久代被移除，换成**元空间（Metaspace）**，改用**本地内存**，用 `-XX:MaxMetaspaceSize` 控制上限（不设就受物理内存限制）。名字变了、位置也挪了，但「方法区」这个逻辑概念一直都在。它最典型的 OOM 原因是**运行时动态生成类太多**：CGLIB 代理、反射、热部署不停造新类，旧类又回收不掉，元空间就被撑爆了。

**运行时常量池**属于方法区的一部分。`.class` 文件里本身有个常量池，类加载之后它进入方法区的运行时常量池，存的是字面量（字符串、数字）和符号引用。这里有个极易踩的点：**JDK 7 之后，字符串常量池被从方法区挪到了堆里**，`String.intern()` 的行为和它直接相关，面试里「`new String("a")` 创建了几个对象」那类题，考的就是这块知识。

另外几个常见的坑顺手记一下：把「方法区」等同于「永久代」是不对的，JDK 8 之后它是元空间，而且用的是本地内存；把「JVM 内存」等同于「堆 + 栈」也不对，至少还少了方法区、程序计数器和直接内存。不过排查时有个好消息：**OOM 的报错信息本身就能告诉你是哪块区域炸了**，看到 `Java heap space`、`Metaspace`、`Direct buffer memory`、`unable to create native thread` 这几个词，范围立刻就缩小了。

#### 顺带搞懂：栈帧结构（了解即可）

每调用一个方法，JVM 就在**虚拟机栈**里压入一个**栈帧**，方法返回就弹出。栈帧四部分：

- **局部变量表**：存方法的参数和局部变量（包括 `this`）。
- **操作数栈**：计算时的临时工作区。
- **动态链接**：指向运行时常量池中本方法所属类的引用。
- **返回地址**：方法执行完该回到哪一行。

#### 实际会碰到它的 4 个地方（重点）

**① 异常堆栈 —— 每天都在读的「栈帧快照」**

```text
java.lang.NullPointerException
    at com.xxx.Service.foo(Service.java:42)     ← 出事时正在执行的方法
    at com.xxx.Controller.bar(Controller.java:18)
    at java.base/java.lang.Thread.run(Thread.java:833)
```

- 一行 = 一个栈帧，格式是 `类名.方法名(文件名:行号)`。最上面是抛异常处，往下是调用者——**从上往下找自己的代码**，框架包可以跳过。
- **行号对不上 / 显示 `(Unknown Source)`**：线上跑的 jar 和本地代码版本不一致，或编译时关掉了调试信息（`-g:none`）。
- **栈「缺帧」是正常的**：JIT 内联会把小方法的帧合并掉；`native` 方法显示 `(Native Method)`。
- 出现 `Caused by:` 说明是**异常链**，真正的根因往往在最下面的 `Caused by`。

**② `jstack` —— 把某一刻所有线程的调用栈 dump 出来**

```bash
jstack <pid>      # 打印所有线程的调用栈
jstack -l <pid>   # 连持有的锁信息一起打
```

- **CPU 100%**：`top -Hp <pid>` 找到最耗 CPU 的线程 id → `printf '%x\n' <线程id>` 转十六进制 → `jstack <pid> | grep -A 20 'nid=0x<十六进制>'`，看那个 `RUNNABLE` 且反复出现的业务栈。
- **死锁**：`jstack` 会自动检测并打印 `Found one Java-level deadlock:`，直接告诉你是哪两个线程抢哪把锁。
- **线程卡住**：`BLOCKED` = 在等锁；`WAITING on condition` = 在 `wait()` / `await()`。
- 看线程名能猜用途：`http-nio-8080-exec-*`（Tomcat 请求线程）、`DubboServerHandler-*`、`GC task thread` 等。
- 通用套路：**`top -Hp` 定位线程 → `jstack` 看它卡在哪一行**，反复这个循环。

**③ `-Xss` —— 一个线程一个栈**

`-Xss` 设置单个线程的虚拟机栈大小（默认几百 KB ~ 1 MB，看平台和 JDK 版本）。

- **调太小**：栈太浅 → `StackOverflowError`（递归太深、调用链太长）。只影响当前线程，JVM 不一定崩。
- **调太大**：每个线程的栈更占内存，线程一多就 `OutOfMemoryError: unable to create native thread`。
- ⚠️ **最容易误解的一条**：这个 OOM 跟**堆**没关系，是**本地线程创建不出来**。堆调大反而更糟（系统剩余内存更少）。
- **排查方向**：线程数异常多时，先查是不是**线程池没复用、或代码里漏了 `new Thread()`**，别急着调 `-Xss`。

**④ 局部变量是 GC Roots 之一 —— 方法没返回，对象就不能死**

GC 从 GC Roots 沿引用链判断存活，GC Roots 包括：虚拟机栈中**局部变量表引用的对象**、静态变量引用的对象、常量引用的对象、JNI 引用的对象。

只要方法没返回，局部变量指向的对象就被「钉住」，**哪怕后面代码已经用不到它**：

```java
public void handle() {
    byte[] big = new byte[100 * 1024 * 1024];  // 100MB
    doSomethingSlow();   // 跑很久，但 big 还在作用域里 → 100MB 一直占着
}
```

改法：**缩小作用域**、把耗时逻辑挪到 `big` 之前，或老做法 `big = null;`。

> 冷门坑：局部变量表按**槽位（slot）复用**，开着**断点调试**时 JVM 会保留已失效变量的槽位，对象就回收不掉——「加个日志/断点内存表现就不一样了」有时不是错觉。

### 4.4 对象的一生

#### 对象分配策略（先记住这四条）

**第一，对象优先在 Eden 区分配。** 绝大多数对象刚 `new` 出来时都放在新生代的 Eden 里（小对象还会先在 Eden 内部的 TLAB 上分配）；Eden 放不下了，就触发一次 Minor GC。

**第二，大对象直接进入老年代。** 需要**连续内存**的大对象——典型是长字符串和很大的数组——如果在 Eden 和 Survivor 之间来回复制，成本很高（复制算法要整块搬运），所以 JVM 干脆直接把它们放进老年代。阈值由 `-XX:PretenureSizeThreshold` 控制；注意它**只对 Serial 和 ParNew 这两个收集器生效**（Parallel、G1 里这个参数是无效的），而且单位是字节，要写成 `3*1024*1024` 这种形式。日常不常调，但排查「老年代涨得特别快」时值得看一眼。

**第三，长期存活的对象将进入老年代。** JVM 会给每个对象维护一个**年龄计数器**：对象每熬过一次 Minor GC（从 Eden 活到 Survivor，或者在两块 Survivor 之间搬一次），年龄就加一；当年龄达到阈值 `-XX:MaxTenuringThreshold`（默认 **15**）时，下一次 GC 就把它晋升到老年代。默认值是 15 而不是别的数，是因为 HotSpot 只用了对象头里的 **4 个 bit** 来存年龄，最大值恰好就是 15。

**第四，动态年龄判断。** 这是对第三条的「提前晋升」补充，HotSpot 并不死板地等到 15 岁。回收时它会**按年龄从小到大累加 Survivor 中对象的大小**，如果加到某个年龄 x 时，这些对象的总和**超过了 Survivor 空间的一半**（由 `-XX:TargetSurvivorRatio` 控制，默认 50%），那么**年龄大于等于 x 的对象就全部直接进老年代**，不用再等。换句话说，只要 Survivor 快装不下了，同一批同龄对象就会被集体「提前毕业」——这也是线上经常看到对象年龄远没到 15 就已经进了老年代的原因。

> 还有一条配套规则叫「**空间分配担保**」：Minor GC 之前 JVM 会先算一笔账——「最坏情况下所有新生代对象都晋升，老年代放不放得下」，如果放不下就可能直接触发 Full GC。它和上面四条合在一起才算完整的分配策略，排查频繁 Full GC 时会用到。

### 4.5 类加载机制（了解即可，别死磕）

> 先说结论：这节**日常写业务基本用不到**，真正值得记的只有两个点——**① 类加载分几步 ② 双亲委派**。记住下面两段就够了，细节忘了不亏。（真用到它的场景：排查 `ClassNotFoundException` / `NoClassDefFoundError`、依赖冲突、SPI 加载不到实现类。）

**1. 类加载分几步**

把编译出来的 `.class` 文件从硬盘搬进内存、变成程序能用的类，就叫类加载。三步走：

```text
加载 → 连接（验证 → 准备 → 解析）→ 初始化
```

用大白话记：

- **准备**：给静态变量占好位子，先填**零值**（数字填 `0`，引用填 `null`）。
- **初始化**：正式开门，把静态变量改成**代码里真正写的值**。

一句话：**准备阶段填零值，初始化阶段填真值。**

**2. 双亲委派**

加载一个类时，**先让父加载器去加载，父加载器加载不了，才自己加载**。

- **不重复加载**：同一个类最终只会被加载一次。
- **保护核心类库**：你自己写个 `java.lang.String`，会被一路委派到最顶层的 Bootstrap，最后加载的还是官方那个，冒充不了。


### 4.6 垃圾回收

**GC 是什么**

GC 是 **Garbage Collection** 的缩写，中文叫**垃圾回收**，指的是 JVM 自动找出堆里「已经不会再被用到的对象」，把它们占用的内存收回来，好留给新对象使用。

为什么需要它？Java 里 `new` 出来的对象都放在堆上，而堆的大小是有限的（由 `-Xmx` 决定），如果只分配不释放，堆迟早被塞满，于是抛 `OutOfMemoryError: Java heap space`。C/C++ 要程序员自己 `free` / `delete`，忘了就是内存泄漏；Java 把这件事交给了 JVM，所以常说「Java 有自动内存管理」。

但要记住一个前提：**自动回收 ≠ 不会有内存泄漏**。如果你的对象一直被别处引用着（比如往静态集合里越加越多），GC 就认为它还「活着」，照样回收不掉——这正是 Java 里内存泄漏最典型的形态。

**怎么判断对象可以回收：可达性分析 + GC Roots**

主流做法是**可达性分析**：从一组叫 **GC Roots** 的根对象出发，沿着引用链往下找，能被找到的标记为存活，**找不到的就判定为垃圾、可以回收**。GC Roots 主要包括：虚拟机栈中局部变量引用的对象、静态变量引用的对象、常量引用的对象、JNI（native）引用的对象。

这也正好呼应 4.3 里那句话——局部变量是 GC Roots 之一，所以只要方法没返回，局部变量指向的对象就被「钉住」，哪怕后面的代码已经用不到它。顺带记一句：早年的**引用计数**算法解决不了对象之间互相循环引用的问题（A 引用 B、B 引用 A，谁都不为 0），所以现在主流 JVM 都改用可达性分析。

**分代回收：Minor GC 与 Full GC**

回收的时机和范围跟堆的分代结构有关。对象先在 Eden 里分配，Eden 满了就触发一次 **Minor GC**（也叫 Young GC），它只回收新生代，发生频繁但速度快；当老年代也满了，会触发 **Full GC**，回收整个堆（外加方法区），慢得多，线上应当尽量避免频繁 Full GC。

另外，不管是哪种 GC，执行时通常都要**暂停所有业务线程**，这个现象叫 **Stop The World（STW）**。不同垃圾收集器（Serial、Parallel、CMS、G1、ZGC）之间的核心差别，本质上就是**怎么把这个停顿做得更短、更可控**。

**书面定义（面试可以照这句说）**

> GC 是 JVM 提供的一种自动内存管理机制，它通过可达性分析等手段识别堆中的无用对象并回收其内存，从而避免手动释放内存带来的泄漏与悬空指针问题。

### 4.7 JIT

**JIT 是什么**

Java 代码首先被编译为**字节码**，JVM 在运行时通过**解释器**执行字节码。当某部分代码被**频繁执行**时，JIT（即时编译，Just-In-Time Compiler）会把这些**热点代码编译为机器码**，以此来提高程序的执行效率。

```text
源码(.java) --javac--> 字节码(.class) --解释器逐条执行--> 运行结果
                                    \--热点代码被 JIT 编译成机器码--> 缓存进 codeCache
```

**关键点：编译只发生一次**

JIT 会把频繁执行的字节码编译成机器码，**这个过程只发生一次**。一旦字节码被编译成机器码，之后每次执行这部分代码时，**直接执行对应的机器码，无需再次解释**。

**热点探测：靠阈值**

JVM 中有一个**阈值**，当方法或代码块在一定时间内的**调用次数超过这个阈值**时，就会被认定为**热点代码**，然后编译并存入 **codeCache**。

几个概念分清楚：

- **解释器**：逐条执行字节码，保证启动速度。
- **JIT 编译器**：把热点代码编译成机器码，提升运行效率。
- **热点代码**：调用次数超过阈值的方法 / 代码块。
- **codeCache**：存放 JIT 编译产物（机器码）的区域。
- **阈值**：判定「够不够热」的标准，超过才会触发编译。

一句话：**解释器负责「先跑起来」，JIT 负责「跑得快」——热点代码编译成机器码缓存起来，之后直接执行机器码。**

#### C1 和 C2 的区别

HotSpot 的 JIT 里其实有**两个编译器**：**C1（Client Compiler）** 和 **C2（Server Compiler）**。可以记成「一个编译得快、一个优化得狠」。

- **别称**：C1 是 Client Compiler；C2 是 Server Compiler / Opto。
- **取向**：C1 追求**编译快**，尽快出机器码；C2 追求**跑得快**，愿意花时间做优化。
- **编译速度**：C1 快；C2 慢（慢一个数量级也正常）。
- **优化强度**：C1 浅，只做基础优化；C2 深，激进优化。
- **生成代码质量**：C1 一般；C2 更高。
- **适用场景**：C1 适合客户端程序、启动阶段、短任务；C2 适合长期运行的服务端程序。
- **典型优化**：C1 做方法内联、去虚拟化、冗余消除、装箱消除；C2 在 C1 基础上再加**逃逸分析、标量替换、锁消除、循环展开**。

**分层编译（Tiered Compilation）**：Java 7 起默认开启，把「解释器 + C1 + C2」一起用——先用解释器和 C1 **快速跑起来**，等这段代码真的「够热」，再交给 C2 精雕细琢。共 5 个层级：

```text
0 解释执行  →  1 C1(不采集)  →  2 C1(少量)  →  3 C1(完整 profiling)  →  4 C2
   冷代码                                                          越来越热
```

- 层级越高，优化越狠、编译越慢；大多数方法走 `0 → 3 → 4`。
- 常用参数：`-XX:-TieredCompilation`（关掉分层，直接上 C2）、`-XX:TieredStopAtLevel=1`（最多到 C1，常用于缩短启动时间）、`-XX:+PrintCompilation`（打印编译日志，看谁被编译了）。

> 补充：JDK 9 之后 `-client` / `-server` 已名存实亡，两个编译器都在同一个 VM 里；JDK 10 起还引入了实验性的 **Graal**（通过 JVMCI）作为 C2 的替代。

#### 逃逸分析（Escape Analysis）

**一句话：分析一个对象会不会「逃出」当前方法 / 当前线程的作用范围。** 如果算出来**不逃逸**，JVM 就敢对它做更激进的优化。

两种逃逸：

- **方法逃逸**：对象被作为返回值给出去、被存进别处能访问到的字段、或传给别的方法。→ 跑出了这个**方法**。
- **线程逃逸**：对象被赋给**静态变量**、或能被其他线程访问的实例字段。→ 跑出了这个**线程**。

判定「不逃逸」后，C2 能做三件事：

1. **栈上分配**：既然对象不会跑出去，就没必要放堆里，可以放到线程私有的**栈**上，随方法出栈一起销毁，省掉 GC 的开销。
2. **标量替换**：标量 = 基本类型，聚合量 = 对象。既然对象不逃逸，那就**干脆别创建它**，直接拆成几个成员变量放在栈上。（HotSpot 里「栈上分配」实际就是靠标量替换落地的，并没有真正把整个对象搬到栈上的实现——这是逃逸分析最主要的收益。）
3. **同步消除**：对象不逃逸、只有一个线程能碰它，那加在它上面的**锁**（`synchronized`）就可以直接删掉。

```java
public int sum() {
    Point p = new Point(1, 2);   // p 只在本方法内用 → 不逃逸
    return p.x + p.y;
}
```

相关参数（默认都开）：

- `-XX:+DoEscapeAnalysis`：开启逃逸分析
- `-XX:+EliminateAllocations`：开启标量替换
- `-XX:+EliminateLocks`：开启同步消除

#### 高频场景：现象 → 说明 → 怎么解决

JIT 平时感知不到，但一旦出问题，**表现几乎都是「性能随时间变化」**。下面 8 个是容易撞到的。

**① 刚启动慢，跑几分钟就快了 —— 预热**

- **现象**：压测/上线初期 RT 高、TP99 抖，跑几分钟后自己稳定。
- **说明**：热点代码还没到阈值、没被 C2 编译完，还在解释执行/C1，这就是**预热**，正常现象不是 bug。
- **解决**：上线前**预热流量/预热脚本**，核心接口先跑一遍；网关**逐步放量**；别拿"刚启动那一下"当结论。

**② 跑几天后性能突然掉、CPU 升高 —— codeCache 满**

- **现象**：长期运行的服务某天开始变慢，日志出现 `CodeCache is full. Compiler has been disabled`。
- **说明**：JIT 编译产物把 **codeCache 塞满**，编译器被禁用，之后的代码**退化成解释执行** → 越跑越慢。
- **解决**：调大 `-XX:ReservedCodeCacheSize`；重点是查**谁在疯狂生成类**（CGLIB/Javassist 动态代理、反射、脚本引擎、热部署）；用 `jcmd <pid> Compiler.codecache` 或启动加 `-XX:+PrintCodeCache` 观察。

**③ 同一方法反复重编 —— 去优化（deoptimization）**

- **现象**：`-XX:+PrintCompilation` 里同一方法编了又编、出现 `made not entrant`，编译线程 CPU 很高。
- **说明**：JIT 做了乐观假设（如"这里是单态，直接内联"），结果**同一位置传进多种类型**，假设被打破，只能退掉重编。
- **解决**：减少热路径上的**多态爆炸**——接口/父类被多种实现混用、集合混放多种类型、滥用反射和动态代理都会加剧；热路径方法尽量 `final`/私有（利于内联）。

**④ 微基准测试结果不可信 —— 没预热 + 死代码消除**

- **现象**：`main` 里跑一次测耗时、两次差十倍，跟线上对不上。
- **说明**：混进了 **JIT 编译时间**，加上**死代码消除**把待测那段直接优化没了。
- **解决**：用 **JMH**（预热、多轮、返回值消费都处理好了）；退而求其次至少加预热轮次 + 把结果**打印/消费掉**。

**⑤ 本地"循环 new 对象"居然没触发 GC —— 逃逸分析生效**

- **现象**：循环创建几十万对象，本地跑完一次 GC 都没有，怀疑自己判断内存泄漏的方法错了。
- **说明**：**逃逸分析 + 标量替换**把这些不逃逸的对象**优化掉了**，压根没进堆。
- **解决**：要验证对象分配行为，加 `-XX:-DoEscapeAnalysis` 关掉再测；别拿"本地没 GC"当"线上不会 OOM"的证据。

**⑥ 担心 `synchronized` 太慢 —— 锁消除**

- **现象**：为了"性能"把单线程逻辑也去无锁化，代码搞得很复杂。
- **说明**：**锁消除**（不逃逸的锁直接被删）+ 无竞争时的轻量级锁，开销本来就很低（偏向锁 JDK 15 起已默认禁用）。
- **解决**：**没竞争别过度优化**，可读性优先；真正该管的是**高竞争**临界区——缩小它，或换成分段锁/无锁结构。

**⑦ 短生命周期任务启动慢 —— 编译 + 类加载开销**

- **现象**：函数计算、批处理任务，干活没几步，"启动 + 首次执行"却占了大头。
- **说明**：**类加载 + 分层编译**本身的开销盖过了业务执行。
- **解决**：`-XX:TieredStopAtLevel=1`（只用 C1，牺牲峰值换启动）；AppCDS 加速类加载；更彻底上 GraalVM Native Image / AOT。

**⑧ 压测曲线"台阶式"跳变 —— 刚好跨过编译阈值**

- **现象**：QPS/RT 曲线平稳一段时间后**突然上下一个台阶**。
- **说明**：某热点方法**刚跨过阈值**被编译（或反过来被去优化）。
- **解决**：多数是正常现象，用**预热**抹平；曲线异常抖动时配合 `-XX:+PrintCompilation` 对齐时间点找原因。

**观察三板斧**：`-XX:+PrintCompilation`（看编译/去优化）、`-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining`（看内联）、`jcmd <pid> Compiler.codecache` + `jstat -compiler <pid>`（看 codeCache 与编译统计）。

### 4.8 性能监控工具

> 对应小册第 15 章。核心就一句话：**先 `jps` 找到进程 → 再用 `jstat` / `jmap` / `jstack` 分头查 GC / 内存 / 线程，而 `jcmd` 一个顶一串。**
> 这些都是 JDK `bin` 目录**自带**的，免安装、**免重启**、生产上可以直接用（Windows 下带 `.exe` 结尾，用法一样）。

#### 六件套：分别干什么

**jps**（类比 Linux 的 `ps`）

- 干什么：看有哪些 Java 进程和 PID（其它工具都要先拿到 PID）。
- 关键选项：`-q` 只输出 PID；`-l` 输出主类全名 / jar 路径；`-m` 输出 main 参数；`-v` 输出 JVM 参数。

**jstat**

- 干什么：看 GC、类加载、JIT 的**运行时统计**。
- 关键选项：`-class` 类加载；`-gc` 堆与 GC；`-gcutil` 只看百分比；`-gccause` 多带「上次 GC 原因」；`-compiler` JIT 统计；`-printcompilation` 最近被编译的方法。

**jinfo**

- 干什么：查看（部分可改）JVM 参数。
- 关键选项：`-flags` 启动参数；`-sysprops` 系统属性。

**jmap**

- 干什么：**堆快照**，查内存泄漏的主力。
- 关键选项：`-histo` 对象统计（按占用排序）；`-dump:format=b,file=heap.hprof` 导出堆快照；`-heap` 堆与收集器概况；`-F` 强制。

**jstack**

- 干什么：**线程栈**，查死锁 / 死循环 / 长时间等待。
- 关键选项：`-l` 附带锁信息；`-m` 带 native 栈；`-F` 强制。

**jcmd**（瑞士军刀）

- 干什么：多功能，**一个顶多个**。
- 关键选项：`jcmd <pid> help` 列出该进程支持的命令；`jcmd -l` 列进程。

#### jcmd 的等价关系（记这个最省事）

- `Thread.print` ≈ `jstack <pid>`
- `GC.class_histogram` ≈ `jmap -histo`
- `GC.heap_dump` ≈ `jmap -dump:format=b,file=xxx`
- `VM.flags` / `VM.system_properties` ≈ `jinfo -flags` / `jinfo -sysprops`
- `Compiler.codecache`：codeCache 用量（见 4.7）
- `VM.uptime` / `VM.version` / `PerfCounter.print`：运行时长 / 版本 / 性能计数器

#### `jstat -gc` 的列，别记错 ⚠️

- **`YGC` / `YGCT`**：Young GC（Minor GC）的次数 / 耗时。
- **`FGC` / `FGCT`**：Full GC 的次数 / 耗时。
- **`GCT`**：GC 总耗时。
- 容量列：`S0C/S1C/S0U/S1U`（两个 Survivor）、`EC/EU`（Eden）、`OC/OU`（老年代）、`MC/MU`（元空间）。其中 `C` = Current 当前容量，`U` = Used 已用。
- ⚠️ **不是** `GC` / `GCC`——那是小册原文的笔误。记住"**Y = Young，F = Full，GCT = 总计**"就不会错。

#### jstack 抓死锁（经典场景）

两个线程**按相反顺序**拿 `lock1` / `lock2`，各自持有对方要的锁 → 互相等，卡死：

```java
synchronized (lock1) { ... synchronized (lock2) { ... } }   // 线程 A
synchronized (lock2) { ... synchronized (lock1) { ... } }   // 线程 B
```

`jstack <pid>`（或 `jcmd <pid> Thread.print`）的输出里会直接给一句 `Found one Java-level deadlock:`，并把互相持有的锁列清楚。

排查口诀：**线程卡住 → 先 jstack 看"栈顶在等什么锁、这把锁被谁持有"**。

#### 操作系统级工具（JVM 之外的，排查时一起用）

- `ps`（Windows 用 `tasklist`）：看进程的 CPU / 内存，如 `ps -ef`。
- `vmstat`：看 CPU、内存、swap，如 `vmstat 1 3`（每秒采一次，共 3 次）。
- `iostat`：看 CPU + 磁盘 IO，如 `iostat -x 1`，重点看 `%util`（磁盘繁忙度）、`await`（IO 平均等待）。
- `netstat`：看网络连接、路由表，如 `netstat -anp`。

#### 堆快照（heap dump）是什么

一句话：**给某一时刻的整个 JVM 堆拍一张「照片」，存成文件（一般是 `.hprof`）。**

- **堆**：拍的是**堆内存**（不是栈、不是方法区），也就是所有 `new` 出来的对象和数组。
- **快照**：是**某一瞬间**的定格。堆里的对象一直在创建、释放、改字段值，dump 出来的只是那一刻的静态影像，拍完就冻住了，之后堆怎么变都不影响这个文件。

**快照里存了什么（关键）**

它不只记录「有哪些对象、每个多大」，还一起存下了**对象之间的引用关系**。所以拿到一份 dump，能回答两个问题：

- **谁占内存**：哪个类的实例特别多、特别大。
- **为什么回收不掉**：是谁还在引用它——顺着引用链往上找，就能找到把它「钉住」的那个 **GC Root**。

第二点才是排查内存泄漏的核心：泄漏的本质不是「对象多」，而是「**对象本该死了，却还有人引用着**」——只看数量看不出来，必须看引用链。

**怎么抓**

- **手动抓**：`jmap -dump:format=b,file=heap.hprof <pid>`，或等价的 `jcmd <pid> GC.heap_dump <路径>`（`format=b` 表示二进制格式）。jconsole / VisualVM / Arthas 里也有按钮。
- **自动抓**：启动参数 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dumps`，**OOM 的那一刻自动 dump**。生产上基本必配——不然等你去连，现场早就没了。

**代价（要知道）**

- 抓的瞬间会 **STW**（暂停所有业务线程），大堆可能要几秒到几十秒。
- **文件很大**，基本和堆一样大甚至更大（堆 4G 可能出来 4G+），**磁盘要留够**。
- 二进制格式**不能直接读**，要用 **MAT**（Eclipse Memory Analyzer）、JProfiler、VisualVM 这类工具打开分析。

**和 `jmap -histo` 的区别（容易混）**

- `jmap -histo <pid>`：**轻量**，只给「类和实例数量 / 占用大小」的汇总，**不含引用关系**，不用落文件，随时能看。
- `heap dump`：**重量**，是完整影像，**含引用关系**，要落文件、要工具分析。
- 打个比方：`jstat -gc` 像体温计，`jmap -histo` 像验血报告（只看指标），**heap dump 像 CT 片子（能看到结构、追出因果）**。

#### 可视化工具怎么用

一句话：**可视化工具就是把前面那些命令行工具「画成图」**——`jstat` 的数字变成曲线，`jstack` 的文本变成线程列表，`jmap` 的 hprof 变成能点的树。主角有四个：jconsole、VisualVM、JFR+JMC、MAT。

**① jconsole —— 最快最简陋，JDK 自带**

- 怎么开：命令行敲 `jconsole`，或 `jconsole <pid>` 直连。就在 `$JAVA_HOME/bin` 里，不用装。
- 概览页：堆内存、线程数、已加载类、CPU 四条曲线，先扫一眼有没有异常。
- 内存页：把 Eden / Survivor / Old / Metaspace 各内存池画成曲线，右下角有「执行 GC」按钮（等价 `System.gc()`，生产别乱点）。**看老年代是不是"降不下去"，就是判断泄漏的第一步。**
- 线程页：每个线程的栈 + 「检测死锁」按钮（等价 `jstack` 里找 `Found one Java-level deadlock:`）。
- 类页 / VM 概要页 / MBean 页：类加载数量、JVM 参数和系统属性（等价 `jinfo -flags`）。
- 特点：零成本、启动快，但**不保存历史**，关了就没数据，适合本地快速看一眼。

**② VisualVM —— 功能最全的瑞士军刀**

- 怎么开：以前 JDK 自带（`jvisualvm`），**JDK 9 起从 JDK 移除**，要单独去官网下载。
- 抽样器（Sampler）：CPU 抽样告诉你**哪个方法最耗 CPU**，内存抽样看**哪些对象在不停被创建**——这是 jconsole 没有的。
- Profiler：更详细，但**有性能开销**，一般只在测试环境用。
- 直接打开 hprof：`文件 → 装入 → 堆转储`，不装 MAT 也能看个大概。
- 最值得装的插件 **Visual GC**：把 Eden、两个 Survivor、老年代的**实时变化画出来**，对象怎么从 Eden 挪到 Survivor、怎么晋升老年代，一眼就懂，比看 `jstat -gc` 的数字直观得多。
- 还能同时连多个进程、连远程。

**③ JFR + JMC —— 生产环境唯一"敢开"的**

- JFR（Java Flight Recorder）是 JDK 自带的**飞行记录仪**（飞机黑匣子）：以**极低开销（通常 <1%）**连续记录 GC、对象分配、线程、锁竞争、IO、异常、JIT 等几百种事件。
- 启动时开：`-XX:StartFlightRecording=filename=app.jfr,duration=60s`。
- 运行中抓（**免重启**）：`jcmd <pid> JFR.start`，录一会儿再 `jcmd <pid> JFR.dump`。
- 产出的 `.jfr` 用 **JMC** 打开分析（`jmc` 命令启动，JDK 11 起也要单独下载）。
- 为什么重要：其它工具要么开销大（Profiler）、要么只能看当下（jconsole）、要么要停机抓（dump）；**只有 JFR 是「低开销 + 可长时间 + 事后回溯」**。线上说不清的问题，先录两分钟再慢慢分析。

**④ MAT —— 专门啃堆快照的**

打开 dump 后重点看四处：

- **Leak Suspects（泄漏疑点）**：自动跑一遍，直接给"疑似哪里泄漏"的报告，**先看这个**。
- **Histogram**：按类看实例数和浅堆（shallow heap）。
- **Dominator Tree（支配树）**：按**独占内存**从大到小排，比 Histogram 准——一个对象可能被很多小对象引用，光看它自己的大小看不出来。
- **Path to GC Roots（排除弱引用）**：选中可疑对象 → 看引用链 → **谁在引用它，谁就是元凶**。
- 进阶：**Compare Basket** 可以对比两份 dump（就是 4.9 里那一步）。
- ⚠️ 坑：MAT 自己也要内存，打开几个 G 的 dump 前先改 `MemoryAnalyzer.ini` 里的 `-Xmx`，不然它自己先 OOM。

**怎么选（按场景对号入座）**

- 本地随手看一眼 → jconsole
- 想看热点方法 / 对象分配 / 分代变化 → VisualVM（+ Visual GC 插件）
- 生产上敢长期开的录制 → JFR + JMC
- 分析内存泄漏的 hprof → MAT
- 只想在服务器上敲命令、不开图形界面 → Arthas

#### Arthas 常用命令

一句话：**Arthas 是阿里开源的 Java 诊断工具，用「attach 到进程」的方式在线排障——不用重启、不用改启动参数、不用开 JMX，交互式敲命令。** 前面 `jstack` / `jmap` / `jstat` 能干的它基本都能干，还多了一样：**能看到方法级别的运行时数据**（入参、返回值、耗时）。

**怎么启动**

- 下载并启动：`curl -O https://arthas.aliyun.com/arthas-boot.jar`，然后 `java -jar arthas-boot.jar`。
- 启动后会**列出机器上所有 Java 进程**，输入序号就 attach 上去（基于 JDK 的 Attach 机制）。
- 它要求和目标进程**同机器、同用户**；远程场景用 `tunnel` 或装 agent。
- 官方文档：arthas.aliyun.com。

**① 先看全局**

- `dashboard`：**最常用**，一个实时面板把线程、内存、GC、Runtime 信息一起显示（相当于 `top` + `jstat` 合体）。
- `jvm`：JVM 的内存、GC、线程、文件描述符、启动参数等汇总。
- `thread`：线程信息。
  - `thread`：列出所有线程，按 CPU 占用排序。
  - `thread <id>`：看某个线程的栈。
  - `thread -n 3`：最忙的 3 个线程。
  - **`thread -b`**：找出**阻塞了其他线程的那个线程**——查「卡死 / 死锁」最快的一招。
  - `thread --state BLOCKED`：只看阻塞状态的线程。
- `sysprop` / `sysenv`：系统属性和环境变量。

**② 找类、看代码**

- `sc -d com.foo.Bar`：Search Class，查已加载的类（`-d` 看详情，含类加载器）。
- `sm -d com.foo.Bar`：Search Method，查类里的方法。
- `jad com.foo.Bar`：**反编译已加载的类**——线上跑的到底是哪版代码，一眼看穿（排查「源码和线上不一致」）。
- `classloader -t`：类加载器树，查依赖冲突用。

**③ 观测方法（Arthas 的杀手锏）**

- `watch`：观测方法的**入参 / 返回值 / 异常**。
  - 例：`watch com.foo.Bar method '{params, returnObj, throwExp}' -x 2`（`-x 2` 展开两层）。
  - 加 `-b`（before）/ `-s`（success）/ `-e`（exception）/ `-f`（finish）控制时机。
- `trace`：**追踪方法内部的调用路径和每步耗时**，定位「慢在哪一行」的神器。
  - 例：`trace com.foo.Bar method`，可加 `'#cost > 100'` 只显示耗时超过 100ms 的调用。
- `stack`：看这个方法**被谁调用**（输出调用栈）。
- `monitor`：方法调用的**统计**（次数、成功率、平均 RT），例 `monitor -c 5 com.foo.Bar method`。
- `tt`（Time Tunnel）：**记录**一段时间内的方法调用（入参 + 返回值），之后**回放 / 重放**，用来复现问题。
- `profiler start` / `profiler stop`：生成**火焰图**（基于 async-profiler），排 CPU 热点。

**④ 查内存、看静态字段**

- `heapdump /tmp/dump.hprof`：抓堆快照（等价 `jmap -dump`）。
- `getstatic com.foo.Bar cache`：**看类的静态字段**——静态 Map 是不是越加越多一眼就看出来，非常适合定位静态集合导致的内存泄漏。
- `logger -n com.foo -l debug`：**在线改日志级别**，临时给线上开 debug 不用重启。

**⑤ 改代码（高风险，慎用）**

- `jad --source-only com.foo.Bar > /tmp/Bar.java` → 改完 → `mc /tmp/Bar.java` 内存编译 → `redefine /tmp/Bar.class` **热替换**。
- 注意：**只能改方法体，不能改方法签名、不能加字段**。
- `ognl`：执行 OGNL 表达式（能调静态方法、改静态字段），威力大、风险也大。
- 这类命令要先 `options unsafe true` 才放行。

**⑥ 退出**

- `exit` / `quit`：只退出当前会话，Arthas 还挂在那儿。
- `stop`：**重置被增强过的类**并退出，收工时用这个。
- `shutdown`：直接关闭 Arthas 服务端。

**使用注意（重要）**

- `watch` / `trace` / `stack` 都是靠**字节码增强**实现的（会临时改类），**有性能开销**——排查完记得停，别在生产核心链路上长期挂着 `trace`。
- `redefine` / `retransform` / `ognl` 属于「改运行时」，风险高，非必要不用。
- 优势总结：**不用重启、不用改启动参数、不用开 JMX 端口、交互式**，还能看到方法级运行时数据——这是它比 `jstack` / `jmap` 强的地方。

#### 一句话记忆

- **`jps` 找人 → `jstat` 看 GC/JIT → `jmap` 挖内存 → `jstack` 看线程 → `jcmd` 都能干。**
- 记不住那么多命令时，先敲 `jcmd <pid> help`，很多单一命令都能被它替代。
- 想**在线看方法级数据**（入参、返回值、耗时）时，命令行工具都做不到，得上 `Arthas` 或 `JFR`。

### 4.9 实战排查

#### 内存泄漏：用堆快照一步步找

1. 先 `jstat -gcutil <pid> 1000`，确认老年代是不是一直涨、Full GC 之后也降不下去。
2. 隔一段时间抓**两份** dump（比如间隔 1 小时）：`jcmd <pid> GC.heap_dump /path/a.hprof`。
3. 用 MAT 对比两份，看**哪个类的实例数量 / 占用大小在明显增长**。
4. 对这个类用 **Path to GC Roots**（排除弱引用），看是谁在引用它。
5. 罪魁祸首基本就三类：**静态集合越加越多、缓存没设过期、监听器没注销**。
